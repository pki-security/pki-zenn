証明書の更新ジョブを頻繁に動かすことと、失敗した発行要求を頻繁に繰り返すことは違います。ジョブを増やした結果、同じ設定エラーを繰り返してCAの制限に達する構成では、更新の信頼性は上がりません。

この記事はACME運用の設計表です。2026年10月2日に確認したRFCとLet's Encrypt公式資料に基づきます。特定の公開CAとクライアントで、この表どおりの更新を実測した報告ではありません。

## 4つの予定を分ける

| 予定 | 決めるもの | 残す証拠 |
|---|---|---|
| ジョブを起動する | timer、cron、常駐クライアント | 起動履歴、次回予定 |
| ARIを再取得する | 応答の`Retry-After`とエラー処理 | 取得時刻、応答、次の取得予定 |
| 証明書の更新を試みる | 推奨期間、クライアントの更新判断 | 選択時刻、Order、対象証明書 |
| 発行失敗後に再試行する | 原因修正、CAの応答、backoff | 最初の失敗、回数、前回の試行時刻 |

ARI（ACME Renewal Information）はCAが更新推奨期間を返す拡張です。RFC 9773は期間内の時刻を選ぶ方式を示し、既存のエラー時の待機・再試行条件も適用するとしています。起動周期を短くした場合も、失敗回数と前回時刻を保持する必要があります。[RFC 9773の更新判断](https://www.rfc-editor.org/rfc/rfc9773.html#section-4.2)

上の4行は運用の整理であり、ACMEが定義した4状態ではありません。取得後の配置、reload、利用者への配信確認はさらに別工程です。

## ARIのRetry-Afterと発行エラーの待機を混ぜない

ARIの正常応答に含まれる`Retry-After`は、次に更新情報を確認する時期を示します。証明書の有効期限でも、必ずその時刻に発行する指定でもありません。RFCのARI処理ではエラー時のbackoffが優先されます。[RFC 9773の再取得とエラー処理](https://www.rfc-editor.org/rfc/rfc9773.html#section-4.3)

一方、発行要求のレート制限エラーでは、CAが返した待機条件を読みます。同じヘッダー名だからといって、別のリソースの時刻を流用しません。

| 記録 | 記入例の意味 |
|---|---|
| `ari_checked_at` | いつ、どの証明書の更新情報を確認したか |
| `ari_check_after` | 次の情報取得を予定する時刻 |
| `renewal_window` | CAが返した推奨期間の開始・終了 |
| `renewal_attempt_at` | 今回のクライアントが更新を試みた時刻 |
| `order_retry_after` | 発行失敗後にCAが示した待機条件 |

この項目名は運用台帳の提案で、各クライアントの設定名ではありません。UTCと日本時間を混ぜず、原応答と変換後の時刻を一緒に残します。

## エラーに応じて次の作業を変える

| 観測した状態 | 次にすること | 再申請だけでは解決しない理由 |
|---|---|---|
| DNS APIの権限エラー | 実行主体、対象ゾーン、必要な操作を確認 | 同じ認証情報では書込みに失敗する |
| TXTやHTTP応答が期待値と違う | 今回のChallengeと実際の応答を照合 | 待機だけで名前・値の誤りは直らない |
| `rateLimited` | 制限対象、応答、待機条件を記録 | Accountや名前を変えて原因を隠さない |
| ARI取得の一時的失敗 | 対象版のbackoffと期限監視を確認 | 取得失敗で有効期限は延長されない |
| 不正な更新期間 | 対応実装の代替更新計画を確認 | 不正な時刻をジョブへ登録できない |
| 新証明書は保存済み、配信は旧版 | 配置先、reload、接続先を確認 | 同じ証明書の再発行より配備の修正が必要 |

ACMEのエラー型は[RFC 8555](https://www.rfc-editor.org/rfc/rfc8555.html#section-6.7)を参照します。短いエラー文だけで原因を断定せず、同じ試行のログとDNS・HTTP・TLSの観測結果を対応させます。

## ARI対応だけで制限対象外と決めない

Let's Encryptの公式資料は、ARIによる更新と従来の同一識別子集合による更新を分けています。ARIで置き換える証明書を示し、識別子の一致や既に置換済みでないこと等の条件を満たす更新には免除を説明しています。従来方式には残る制限があります。[Let's Encrypt Rate Limits](https://letsencrypt.org/docs/rate-limits/#limit-exemptions-for-renewals)

これはLet's Encryptの方針です。別のCAにも同じ免除がある、すべてのARI問い合わせまで無制限である、と拡張して読まないでください。Directory、環境、対象クライアント版、実際のOrderの扱いを確認します。数値を手順書へ固定する場合は確認日と見直し担当も付けます。

```text
CAと環境：
Directory URL：
対象証明書と識別子：

起動周期と次回予定：
ARIの取得時刻・推奨期間・再取得予定：
前回の失敗時刻・回数・原因修正：
CAの再試行条件：
配備先と外部確認先：
期限監視・通知先・残り時間が足りない場合の担当：
```

更新情報を取得できなくても、期限監視は継続します。期限が迫る場合は、再試行回数を増やすだけでなく、担当者へ引き継ぎ、対象を固定した復旧手順を選びます。
